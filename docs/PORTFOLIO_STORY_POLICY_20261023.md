# 취업 포트폴리오 기본 작성·검토 원칙

> 2026-10-23 사용자 요청 및 KT 클라우드 현업자 조언을 반영한 기준. **새 채팅/Work/Codex/문서·PPTX·PDF·웹 수정 시 먼저 읽고 적용한다.** 각 프로젝트는 팀이 함께 만든 결과물이며 개인 업무 감사표가 아니다.

## 1. 가장 중요한 목표

- 신입·주니어 Cloud Infrastructure / DevOps / SRE / Platform 채용 담당자에게 **어떤 서비스를, 어떤 기술과 협업으로 구현·운영·검증했는지** 빠르게 보여준다.
- 프로젝트의 기술적 가치·전체 아키텍처·팀 성과를 충분히 소개한다. **개인 범위만 잘라 나머지 팀 성과를 숨기거나 축소하는 접근을 하지 않는다.**
- 사용자의 담당 업무는 구현 외에 팀장·설계 논의·통합·기술 지원·장애 분석·운영·모니터링·시연·복구 검증·협업까지 실제로 참여한 맥락을 반영해 **적극적이고 설득력 있는 언어**로 표현한다.
- 개인과 팀을 매 문장마다 'MY/PROJECT'로 기계적으로 분할하지 않는다. 필요한 경우 자연어(예: '팀과 구축한', '통합 과정에서', '운영 검증에 참여')로 적는다.
- 다만 **하지 않은 작업을 혼자 수행했다고 주장하거나 실제 없는 데이터·성과·검증 완료·수치를 만들어내지는 않는다.** 표현의 자신감과 허위 주장은 다르다.

## 1-1. 문체: 담백하게 쓰기

- 광고·보도자료처럼 보이는 표현을 피한다. '혁신', '획기적', '완벽한', '압도적', '엔드투엔드 역량 확보'처럼 의미가 넓고 근거가 희박한 수식어를 붙이지 않는다.
- **내가 한 행동 + 확인한 결과**를 짧은 문장으로 쓴다. '문제를 해결하는 과정에서 운영 안정성의 중요성을 깨달았습니다'보다 'Kafka 연결 오류를 NetworkPolicy·TLS·인증·ACL로 나눠 확인했습니다'가 낫다.
- PR 번호·테스트 수·약어를 문장의 주인공으로 두지 않는다. 채용 담당자가 이해할 서비스 구조와 문제 해결 과정을 먼저 적는다.
- 제목과 본문에서 같은 말을 세 번 반복하지 않는다. 비슷한 표현을 AI가 만든 듯 변주하지 않는다.
- 팀이 한 일과 내 경험을 자연스럽게 섞어 기술하되, 역할과 검증 범위를 의도적으로 오해하게 만들지 않는다. 필요한 사실 구분은 간결한 한 문장으로 충분하다.
- 기본은 자연스러운 한국어. 기술 고유명사만 영어 그대로 사용하며 어색한 영문 혼합을 줄인다.
- 결과 아래 회색 주석이나 사진 설명에 '팀 결과', '별도 기록', '측정하지 않음' 같은 단서를 반복하지 않는다. 필요한 조건은 '비동기 요청 수락'처럼 결과 옆에 짧게 적고, 상세 근거와 시점 차이는 내부 기록에 남긴다. (2026-10-25 사용자 요청)

## 2. 권장 프로젝트 설명 순서

1. **프로젝트 소개**: 해결하려는 문제와 서비스 핵심 가치, 2–3문장.
2. **아키텍처·사용 기술**: 실제 구현 기준의 간단한 그림 한 장, 핵심 기술 4–6개. 클라우드 경계·컴포넌트·데이터/요청 흐름 구분.
3. **주요 구현·운영 내용**: 가장 중요한 2–4가지. 팀 프로젝트 전체 경험을 중심으로 작성하고 사용자의 기여를 자연스럽게 드러낸다.
4. **대표 결과·트러블슈팅**: 실제 성공/장애 사례 1–2개와 증거 있는 수치만 강조.
5. **실제 사진·자료**: 본문 가까운 위치에 1–2장. 관련 코드/PR/발표자료 링크는 해당 문장 바로 옆에 짧게. 별도의 빈 '출처 보기/검증 기록' UI를 억지로 만들지 않는다.

PDF/PPTX는 짧은 면접 안내서, 웹은 읽기 쉬운 프로젝트 소개와 선택적 기술 깊이를 담당한다. 모든 정보를 한 페이지에 넣으려 하지 않는다.

## 3. 개인·팀 경험을 소개하는 언어

**우선할 표현**
- '팀과 함께 [서비스]를 구축하고 [문제]를 해결했습니다.'
- '[아키텍처]를 기반으로 [현상]을 분석하고, [운영/통합/검증] 과정에 참여했습니다.'
- '프로젝트에서 [기능]을 구현했으며, 저는 [실제 기여]를 중심으로 담당했습니다.'
- '팀의 [기술] 구현을 통합하면서 [배운 점 / 연결점]을 확인했습니다.'

**지양할 표현**
- 모든 결과에 도장처럼 '팀 성과이므로 내 성과 아님'을 붙이는 방식.
- 프로젝트의 핵심 구조나 실증 수치를 개인 기여 목록에 없다는 이유만으로 삭제하는 방식.
- PR/테스트 식별자·영상 타임스탬프·출처명만 줄줄이 노출하는 방식.
- 작은 구현 경험을 크게 보이게 하려고 수행하지 않은 역할을 단독 수행으로 바꾸는 방식.

## 4. 프로젝트별 유의점

- **Bluebell**: 팀장으로서 AWS Web/WAS 통합, 장애 복구·관측 정상화까지 프로젝트의 전체적인 운영 스토리를 강조. 팀 자동화·DB·모니터링 요소도 프로젝트 소개에 포함.
- **Durian**: Kubernetes/OpenStack + Redis/Kafka/KEDA의 수강신청 대기열/비동기/Autoscaling 전체 흐름을 강조. Kafka Lag 확장 1→4→1, 외부 HTTP 수락, Worker 재가입 등 실제 팀 시험 결과 포함. 사용자 참여는 모니터링·운영·Kafka/KEDA 진단·복구 검증 중심으로 강하게 어필. HTTP 300/300은 요청 수락이지 DB 300개 Commit을 뜻하지 않음.
- **OneReport**: 해커톤 전체 서비스와 AWS PoC를 소개하면서 사용자 Backend/도메인·API 계약·규칙 기반 분석·Smoke 경험을 자연스럽게 서술. PoC와 제안을 혼동하지 않고 실 기관 연동·LLM 분석 완료로 주장하지 않음.
- **Labbit**: 가상 실습 플랫폼 자체의 사용자·Frontend·Backend·OpenStack Workspace 관계를 먼저 소개. Frontend/UX/API·Terminal/File/Live/권한·Flow 통합과 협업 경험을 강조. 코드/CI 병합과 실환경 VM E2E는 혼동하지 않음.

## 5. 시각·링크·검증

- Navy+Teal 기반의 깔끔한 디자인과 실제 프로젝트 자료 우선.
- 수식어보다 명료한 제목, 긴 검증 항목보다 결과를 읽기 쉬운 구성.
- 아키텍처 그림은 **설명용 도식**, 실제 스크린샷은 **검증 장면**으로 구분한다.
- 공개할 수 없는 PR/자료 링크를 만들어 내지 않는다. 불필요한 내부 문서명 표기는 본문에서 걷어낸다.
- 모바일 320/390/768, PC 레이아웃·텍스트 오버플로·링크·키보드·이미지 실제 로딩 검증.
- 기존 본문 삭제/전면 재작성 전 프로젝트 가치와 서술 강도가 떨어지지 않았는지 재확인한다.
- 코드 CI 통과, Preview 브라우저 QA 통과, 운영 배포 READY와 실제 운영 브라우저 확인을 서로 구분한다.
